The boilerplate uses typed errors in `src/lib/errors.ts` and classifies them in `src/lib/handler.ts`.

## Error classes

| Class | Status | Use for |
| --- | ---: | --- |
| `ValidationError` | 400 | Expected invalid input or business-rule failures. |
| `UnauthorizedError` | 401 | Missing or invalid authenticated user. |
| `ServerError` | Custom, default 500 | Expected server-side failures with an explicit status. |

```ts
import { ServerError, UnauthorizedError, ValidationError } from "@/lib/errors";

throw new ValidationError("Invalid plan");
throw new UnauthorizedError();
throw new ServerError("Upstream unavailable", 503);
```

## Response shapes

Queries return:

```ts
{ data: value, error: null }
// or
{ data: null, error: "message" }
```

API routes return:

```ts
{ success: true, data: value }
// or
{ success: false, error: "message" }
```

Server actions use next-safe-action response fields such as `serverError`, `validationErrors`, and `data`.

## App error boundary

`src/app/error.tsx` catches runtime errors in the React tree and renders a user-friendly recovery screen.

## Best practices

- Use typed errors for expected failures.
- Use explicit result unions when callers should branch on success/failure.
- Do not add bare `throw new Error("...")` paths in handlers, actions, or services.
- Keep user-facing messages in `src/locales/index.ts`.
- Log unexpected failures at boundaries with safe metadata.
