# Documentation

`@tstack/docs` is your SaaS product's documentation site. It reuses the official
Cloudflare Nimbus Docs scaffold used by TStack, with neutral product branding
and no link to TStack's repository. The original scaffold was generated with:

```sh
pnpm create @cloudflare/nimbus-docs@0.9.0 docs --yes
```

The generator's `starter` template uses Astro 7 and `@cloudflare/nimbus-docs`
0.20.x. Generator and runtime versions are separate. `nimbus.json` records the
template provenance and registry settings.

The starter's owned layouts, components, theme, routes, search, Markdown
endpoints, and social-image pipeline are retained. Demo pages and the example
partial have been removed. The home page contains only a welcome message;
there are no invented product features or integration instructions.

## Development and checks

Use Node.js 24 or later, Bun `1.4.4` for workspace-local tooling, and the boilerplate's pinned pnpm version. Install
dependencies with `pnpm install` from the boilerplate root
(`packages/boilerplate` inside TStack), then run:

```sh
pnpm --filter @tstack/docs dev
pnpm --filter @tstack/docs lint
pnpm --filter @tstack/docs typecheck
pnpm --filter @tstack/docs build
pnpm --filter @tstack/docs preview
```

Development and preview use port 4324 so this site can run alongside TStack's
own documentation on 4322. The boilerplate's `pnpm dev` starts it automatically.
Both servers use `--ignore-lock` to stay in the foreground
under agents; Turbo or the orb service supervisor owns their lifecycle, not an
Astro background daemon. `lint` runs Nimbus's real documentation checks, including
frontmatter validation and internal links. It builds first because Nimbus needs
the generated `.nimbus/routes.json` manifest to validate links. After a build,
`lint:docs` runs just the content checks. `typecheck` runs Astro Check with the
shared strict TypeScript configuration. There is no placeholder test command.
Search uses the Pagefind index generated by `build`; verify it with `preview`,
not just the development server.

## Project structure

- `src/content/docs/`: English Markdown and MDX pages; files become routes.
- `src/content.config.ts`: Nimbus content collections and frontmatter schema.
- `src/components.ts`: components available in MDX without imports.
- `src/components/`, `src/layouts/`, `src/styles/`: the Nimbus-owned UI scaffold.
- `src/pages/`: documentation routing, Markdown exports, metadata, and images.
- `public/`: static assets and Cloudflare cache headers.
- `astro.config.ts`: site metadata, navigation, and Nimbus integration.
- `nimbus.json`: official template metadata used by Nimbus tooling.

Keep source, comments, documentation, and visible text in English. Add real
guides when their corresponding functionality exists. Pages join the sidebar
automatically; use frontmatter to set titles, descriptions, and ordering.
Consult the [Nimbus documentation](https://nimbus-docs.com/get-started/) for
authoring, component installation, and migration guidance.

## Production configuration

Set `SITE_URL` to the actual documentation origin before building for production.
It controls canonical URLs, sitemap links, Markdown indexes, and social images.
The default is the local development origin, not an invented production domain.
Update the `Your SaaS Docs` title, description, and social-image alt text in
`astro.config.ts`. Add your own `github` URL only if you want a source link.
When building both TStack and the SaaS documentation for publication, invoke
each workspace separately with its own `SITE_URL`.

```sh
SITE_URL=https://your-docs-domain.example pnpm --filter @tstack/docs build
```

The build writes static output to `dist/`. The approved deployment is static assets on Cloudflare through Alchemy `2.0.0-beta.87`, not a Node/static container server. Bun `1.4.4` is workspace-local development/tooling; it does not run inside deployed Workers. Nimbus remains the documentation framework. See the [infrastructure README](../../infra/README.md) for integrated configuration/commands and the [deployment guide](../../docs/stack/deployment.md) for acceptance gates. No deployment is needed for local work, and no cloud operation, including plan/state bootstrap, is authorized here. A local build does not prove deployed canonical links, search or asset behavior.
