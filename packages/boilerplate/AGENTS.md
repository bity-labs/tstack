# Agent Guidance

- Write code, comments, documentation, and README files in English.
- Read [coding standards](docs/coding-standards.md) before editing and [feature architecture](docs/feature-architecture.md) before adding or moving modules. Read [project context](docs/context.md) for product/domain changes and [ADRs](docs/adr/) for architecture decisions.
- Load only the relevant [engineering doctrine](docs/engineering/index.md) and [stack guide](docs/README.md). Reusable workflows are installed locally in `.agents/skills/`; generic guidance does not override this project's stack-specific rules.
- This directory is a standalone pnpm/Turbo workspace. All paths and root commands below are relative to this directory, including when it lives inside the TStack repository. Run `pnpm install` here; use its Turbo scripts for development and checks.
- Applications belong in `apps/*`; shared packages belong in `packages/*`. Keep this workspace usable after copying it outside TStack: no imports, dependencies, or configuration links to its parent repository.
- Keep business API contracts in Effect. Export OpenAPI without starting the server, opening a database or requiring auth secrets; generate the SDK with Orval. Web and mobile consumers call business endpoints through `@tstack/sdk`, not backend imports. Authentication uses the official Better Auth clients; its server and database ownership stay in the API. Read the [auth guide](docs/stack/auth-guide.md) before changing the integration or session behavior.
- Use Effect for backend HTTP, SQL, configuration and scoped resources, with Alchemy and `@alchemy.run/better-auth` pinned to `2.0.0-beta.87`. Use Bun `1.4.4` for local development/tooling and local SQLite fixtures; retain pnpm/Turbo and the existing test runners. Deployed API/web run on Cloudflare Workers (`workerd` with `nodejs_compat`), not Bun or a Node server. D1 is the deployed database; keep runtime imports out of pure contracts.
- Follow [ADR 0006](docs/adr/0006-cloudflare-only.md) for the Cloudflare-only strategy and [ADR 0004](docs/adr/0004-deployment-lifecycle-and-security.md) for lifecycle/security. Use native service bindings for deployed web→API requests while preserving the SDK and official auth clients. Do not add self-hosting, VM, Docker/Compose/Coolify, tunnel or SSH provisioning paths. Read [deployment](docs/stack/deployment.md), [infrastructure](infra/README.md) and [operations](docs/stack/operations.md) before infrastructure changes. Local checks must remain offline; obtain explicit operator approval before cloud operations, including Alchemy plan/dev or state bootstrap. Approved activation of branch automation covers its routine releases only, not local CLI operations, teardown or recovery.
- Keep non-secret deployment configuration in `infra/project.ts`, with a stable distinct `project.name` per application and visible Cloudflare names `<name>-cloudflare-<stage>-<role>` for ownership/cost attribution. Name changes, especially D1/state, can create separate resources; require migration/identity review, not a presumed safe rename. Provision only used resources, no unused buckets. Use Better Auth's native Alchemy state-backed secret for deployments; preserve state/resource identities and review adoption separately for existing external secrets. Local Bun still requires its explicit secret. After one-time operator activation, deploy automatically after successful CI on `staging` to staging and `main` to production, with branch-restricted `cloudflare-<stage>` environments. Pull requests and other branches must not deploy; follow the deployment guide for activation and secret isolation.
- Keep canonical business SQL in `apps/api/migrations`. Preserve existing data, the stable auth secret, legacy `effect_sql_migrations` and checksummed `__alchemy_migrations` history where present; reject edited applied SQL rather than resetting history. Better Auth owns its auth table migrations. SQLite→D1 requires a reviewed export/import, isolated validation and approved cutover; it is not automatic or transparent.
- Keep web UI and Storybook in `apps/web`, and native UI and Storybook in `apps/mobile`. Do not introduce a shared UI package without a second web consumer.
- Put application capabilities under `src/features/<feature-name>`. Keep routes and process entry points as composition code; use feature public entry points instead of deep cross-feature imports. Custom filenames are kebab-case, with the framework/generated exceptions in the coding standards.
- Use Vitest for web, API, SDK and MCP tests, real Bun SQLite subprocesses for local persistence, and local workerd/D1 coverage for deployed adapters; neither storage mocks nor SQLite tests alone prove D1 compatibility. Use Jest with `jest-expo` for mobile unit and component tests.
- Add or update each workspace's README when its commands or configuration change.
