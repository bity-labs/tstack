# Authentication boundaries

The API owns one Better Auth service through `@alchemy.run/better-auth` at `2.0.0-beta.87`, composed with Effect as recorded in [ADR 0006](../adr/0006-cloudflare-only.md). Bun `1.4.4` SQLite is a local development fixture; deployed auth runs on workerd/nodejs_compat with D1, not Bun or a Node server. Browser/native apps retain the official Better Auth React/Expo clients; the Effect HTTP contract and Orval HTTP SDK own business operations such as `GET /me`. There is no second auth server in TanStack Start and no generated replacement for the Better Auth protocol. These boundaries are requirements, not evidence that migration adoption or deployed auth has been verified.

## Server invariants

- Keep origin/CSRF checks, exact trusted web/mobile origins, database-backed rate limiting and the minimum password length. Deployed Better Auth uses its native Alchemy state-backed random secret; preserve state and resource IDs. Local Bun requires an explicit stable `BETTER_AUTH_SECRET`. Never commit secret values or switch an existing external secret without a reviewed adoption; see [secret ownership](../../infra/README.md#better-auth-secret-ownership).
- Preserve database-backed session checks: cookie session caching is disabled. `/me` checks current validity without renewing cookies because SDK SSR callers cannot deliver the API's cookie changes themselves.
- Return only the profile fields in the public `User` schema. Missing, forged, revoked or expired sessions fail with 401; unavailable storage fails closed rather than becoming an anonymous success.
- Sessions expire after seven days and can renew after one day through the official session client. Each device sign-in creates a separate session; sign-out on one device does not revoke every other device.
- Business SQL and auth use the same environment's database (local SQLite fixture or deployed D1) without sharing ownership of auth tables. Better Auth owns its table migrations. Preserve data, migration histories and the existing secret when changing adapters; do not use a reset as an upgrade. SQLite→D1 is not automatic/transparent: review export/import, isolated validation and cutover. Follow [ADR 0004](../adr/0004-deployment-lifecycle-and-security.md) for migrations, secrets and backups.

## Browser invariants

Cookies remain HttpOnly and Secure under HTTPS. The Start proxy relays the original request's cookies/origin metadata and distinct response Set-Cookie headers, with no-store. Deployed proxy and SSR reads use the API Worker service binding; local development uses HTTP. A binding does not make hostile origins trusted or relax CSRF checks. Keep canonical public auth/trusted origins explicit and separate from internal binding request URLs. The request-scoped session function also sets private/no-store and never shares a user snapshot across SSR requests.

The pathless route guard prevents anonymous page loading, but the API remains the security boundary. `AccountScreen` hides the previous user's profile immediately on an identity mismatch and invalidates router data. Keep periodic 60-second revalidation, focus/connectivity refresh, known-expiry hiding and hidden protected UI on revalidation errors. Session changes are bounded polling/signals, not instantaneous server push.

## Native invariants

Use the official Expo client and SecureStore for cookie persistence; disabled optimistic session caching must not become disabled cookie persistence. Native profile calls use `getCookie()` and explicit SDK options. Hide protected content when validity cannot be established.

The pinned Expo plugin clears its cookie before the sign-out request completes. The screen retains an unconfirmed logout credential only in memory, hides protected UI immediately, and retries revocation with that original credential. It blocks another sign-in until confirmation. Do not simplify a retry to an unauthenticated second `signOut()` call. Closing the app before confirmation loses the in-memory retry credential; the original server session can remain valid until expiry. Do not claim cross-restart revocation or persist that credential in ordinary storage/logs.

## Email-code access

Email/password remains available. Web and Expo also use the official `emailOTPClient()` and the API's native `emailOTP` plugin for passwordless sign-in or signup. Better Auth generates and verifies six-digit codes, hashes them in its verification table (`storeOTP: 'hashed'`), expires them after five minutes, allows three guesses, consumes successful codes and rotates codes on resend. No handwritten OTP or password hashing is used. Sending and verification endpoints have database-backed per-path limits of three requests per minute per client IP; requesting more codes does not bypass those HTTP limits.

The API trusts only Cloudflare's edge-supplied `CF-Connecting-IP`, not arbitrary `X-Forwarded-For`. The web proxy preserves that header through the native binding. Public production traffic must enter through Cloudflare; do not remove visitor IP headers with a Managed Transform. Missing trusted IPs use Better Auth's shared fallback bucket, not unlimited sending. Local HTTP is only a development fixture; forwarded headers are not an authentication boundary there. Validate real edge→binding client-IP behavior before public release.

Code sign-in proves email ownership and sets `emailVerified`. For an existing **already verified** account, the password and other sessions remain. For an existing **unverified** account, the pinned Better Auth plugin first deletes unproven account links (including its password) and revokes prior sessions before issuing the mailbox owner's session. This prevents account pre-hijacking; do not disable it or promise existing unverified passwords survive. Password registration alone still does not prove email ownership. Password recovery, a separate verification campaign, MFA, roles, tenancy and social providers have no UI/workflow configured. Native plugin endpoints are not a substitute for those product flows. Private MCP tools need a separate authenticated transport design; the current MCP tool only checks public API health.

### Local capture versus real delivery

Ordinary `pnpm dev` writes JSON email messages to `apps/api/.local/emails`, or `AUTH_EMAIL_DIRECTORY` relative to the API working directory. Messages contain `to`, `subject` and `text`; open the newest relevant file privately and enter its code. Files are created exclusively with mode 0600 in a mode-0700 directory and are Git-ignored. They contain usable credentials: never serve them, commit them, put them in screenshots/logs, or reuse the capture transport in production. Delete local messages when finished; no automatic mailbox retention policy is configured.

Deployed delivery uses Cloudflare **Email Sending**, not IMAP or inbound forwarding, through Alchemy's native `SendEmail`/`Send` binding restricted to `project.emailFrom` in `infra/project.ts`. The sender must be an address on the configured Cloudflare zone/subdomain with Email Service domain onboarding/authentication completed. Infrastructure validation checks syntax/zone membership, not deliverability. The small `await-email-delivery` context plugin replaces the pinned integration's error-swallowing background behavior: delivery failure becomes a generic no-store 503, not a success acknowledgement. It does not implement OTP cryptography, storage or sessions. Success means provider acceptance, not guaranteed inbox arrival.

Cloudflare currently permits free sending to verified destination addresses; arbitrary recipients require Workers Paid and its sending allowance/overage. See [Email Sending pricing](https://developers.cloudflare.com/email-service/platform/pricing/) and [setup](https://developers.cloudflare.com/email-service/get-started/). This is distinct from recipient inbox access: there is no IMAP integration here. Offline capture is the default because it needs no credentials, sends no real emails, does not consume quotas and works without a network. Real Cloudflare delivery from a local integration run remains separately authorized operator work; there is no credential-bearing local sending switch or automatic cloud bootstrap in `pnpm dev`.

## Integration verification

Retain the same server, browser and native invariants when changing the backend integration. Test register/sign-in, `/me`, renewal, expiry/revocation, hostile origins, storage failure, separate device sessions and sign-out. Cover email-code signup, replay, expiry, guesses, resend, throttling, delivery failure and verified/unverified existing-account promotion. Verify restart/redeploy preservation with the same database and secret, SSR request isolation, no-store, distinct Set-Cookie forwarding and missing-binding failure. Native Jest mocks cover UI behavior, not real SecureStore/network behavior; API integration needs real Bun SQLite and local workerd/D1 coverage under Vitest. Local SQLite alone cannot prove D1 execution/limits or deployed auth. Existing-data adoption, live routes/bindings, cookie/origin behavior, Cloudflare Email delivery and isolated D1 recovery remain separately approved deferred checks in the [deployment guide](deployment.md); no cloud operation, even plan/state bootstrap, is authorized here.
